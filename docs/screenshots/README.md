# Screenshot evidence

- `belay-cockpit-approval.png`: live capture (2448×1406) of the pending human approval intercept, taken against the seeded VPS deployment through an SSH tunnel. Shows requester, target, digest, expiry, and policy reason for a real `demo-staging-reload` request. No secret value or browser session token is present.
- `belay-cockpit-fail-closed.png`: live capture (2448×1406) of a genuine `indeterminate` outcome, taken against the seeded VPS deployment through an SSH tunnel. `demo-vault-reload` (a companion to `demo-staging-reload` registered in `packages/daemon/src/executor/command-registry.ts`) requires one vault-held environment variable; approving it while the vault is locked or unconfigured (the default state) makes execution throw `VAULT_LOCKED`, and the approval is recorded as `indeterminate` rather than silently succeeding or retrying. Reproduce with `npm run demo:request-vault-approval`, then approve the resulting card in the Cockpit. This is one of two paths to `indeterminate` -- the other, a daemon crash mid-execution, is described in `docs/threat-model.md` and covered by `recoverAmbiguousApprovals` at startup.

Cloud Console and Gemini response captures remain manual because they must be reviewed for account identifiers and credentials before inclusion. The exact non-image evidence is in `docs/hackathon-build/cloud-run-evidence.md`.
